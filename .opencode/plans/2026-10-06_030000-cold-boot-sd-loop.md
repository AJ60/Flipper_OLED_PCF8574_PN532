# Plan: Nail Down Cold-Boot SD Bootloop (Post-Momentum-Replace, Post-SD-Watchdog-Fix)

## Goal
Find the exact fault that resets the device when it boots with an SD card inserted, then fix it.

## Current State (verified)
- Momentum app replaced with reference implementation (`lib/momentum/asset_packs.c`, `momentum_app`).
- `furi_hal_sd.c` : no `furi_check` on SPI transfers (soft errors), no shared-pin grounding in power reset, mount retries 3→10, init retries 3→32, IWDG refreshed in all block-level retry/poll loops.
- `furi_hal_watchdog.c` : IWDG reload 500→2000 (~4 s → ~16 s).  Note: current on-disk content still says `500` (reverted somehow) — needs verification before flashing.
- Cold boot **with** SD: pictures of icons/animations play, then reset, forever.
- Cold boot **without** SD: normal boot.
- Hot-swap while running: SD ever mounts (`L0_SdBad`, all `/ext/...` files give `Status [2]`), no reset loop; stack watermark warnings (`112`, `196`) present.

## What This Tells Us
1. The bootloop is a **cold-boot-only** path, while the hot-swap path stays alive — so the reset is not a raw SD SPI timeout (those are all soft errors now) and is not a RAM exhaustion in the normal service loop.
2. The cold-boot path additionally executes, inside `furi/flipper.c::flipper_init()`:
   `flipper_migrate_files()` → `namespoof_init()` → `momentum_settings_load()` → `asset_packs_init()` (only when SD mounts),
   and the splash slideshow when available.
3. The observed "momentum stuff loading one by one, then reset" is consistent with a crash during **asset-pack symbol initialization or slideshow playback from the SD card**, or during `storage_migrate`* copy of files, or the moment the Dolphin/firstboot animation starts to draw with SD-loaded frames.

## Architecture / Approach
Diagnose with the existing in-firmware fault report (no extra hardware needed), then apply a targeted software fix.

Do NOT copy more code from the reference; do NOT touch the SD SPI fixes further until we know the fault message.

## Step-by-Step Tasks

### Task 1 — Get the actual crash message (highest priority)
The boot reset likely calls `furi_crash()` or a `furi_check()` with a message; STM32 backup registers keep it, and `desktop_scene_fault` prints "Flipper crashed and was rebooted / <message>" full-screen for 3 s right after each reboot.

- Start the loop (SD in, power on). Watch the OLED *after the last animation and just before each reset*: note every text line that appears for those 3 s.
- If the screen shows only the updating logo and restarts, then the loop is **not** a `furi_crash` — go to Task 4.

### Task 2 — If no crash popup: instrument the loop boundary
In `furi/flipper.c`, around the boot path, add `FURI_LOG_I(TAG, "BOOT stage <N>");` right before each of:
- `flipper_migrate_files()`
- `namespoof_init()`
- `momentum_settings_load()`
- `asset_packs_init()`

and after service starts: `FURI_LOG_I(TAG, "all services started")`.
Rebuild (`fbt.cmd firmware_all`), flash, power up with SD inserted, and watch USB serial. The **last printed stage** locates the crash.

### Task 3 — If the culprit is `asset_packs_init` or slideshow, patch it
Likely crash site given an on-SD pack: `lib/momentum/asset_packs.c`
```c
    AnimatedIconSwap* swap = malloc(...);          // no NULL check
    swap->frames[i]    = malloc(frame_size);       // no NULL check, no sanity on frame_size
```
`malloc` failure → `storage_file_read` through a NULL pointer → `furi_crash` → loop.
Fix:
- NULL-check every `malloc` in `asset_packs.c`; on failure free and skip that symbol (log `FURI_LOG_E`).
- Sanity-clamp `meta.frame_count` to e.g. 64 and animation `frame_size` to 64 KiB.
- Bail out cleanly from `asset_packs_init` leaving `asset_packs = NULL` so the device falls back to built-in flash icons (no crash, huge pack still not crashing).

### Task 4 — If the culprit is the storage mount loop itself
- Call `furi_hal_watchdog_iwdg_refresh()` before *and* after every `furi_hal_sd_init()`/`f_mount` attempt on the cold-boot path (one per type), and raise `SD_IDLE_RETRY_COUNT`/`SD_TIMEOUT_MS` sanity.
- Verify `furi_hal_watchdog.c` currently has the 16 s window (file on disk was observed as `500`/"~4 s" after our last edit — needs `git diff` check and re-application if necessary).

### Task 5 — Deal with the mount-failure discrepancy
Hot-swap always ends at `L0_SdBad` (`Status [2]`). Before our power-reset removal both failing mounts and card-present boots behaved alike; now card-out-of-slot mounts on hot-swap always fail while cold boot hangs. Compare `furi_hal_sd_init` coarse behavior (first try success vs `f_mount` retry budget) and consider a modest pin-out power-rail for the SD (`SD{····}`) if the board allows, otherwise increase the post-insert settle delay from 250 ms to 500 ms.

### Task 6 — Rebuild, flash, and validate
```powershell
.\fbt.cmd firmware_all
```
Test:
1. Cold boot, SD in — no loop, desktop reached.
2. Cold boot, SD out — normal boot.
3. Hot-swap — SdBad or mount, but *never* a reset loop (if SdBad is unavoidable that's a separate bug, do not abort this loop fix).
